# Shadow-mode Autoware ADAS プロジェクト ロードマップ（3か月）

更新日: 2026-06-06

補足: 2026-06-06 時点では、ShadowMode / E2E planner 評価の現状まとめを `doc/shadow_mode_e2e_current_status_ja.md`、ChatGPT 相談用ブリーフを `doc/shadow_mode_e2e_chatgpt_consultation_ja.md` に追加している。今後の研究は、まず live shadow-only bag で 10Hz、LiDAR raster、route freshness、target triplet を同時に検証し、その後に camera preprocessing / LiDAR raster / target triplet の A/B を進める。

## 0. プロジェクト概要

### 目標
以下を満たす**シャドーモード自動運転評価プラットフォーム**を構築すること:
- 車両制御を**実際には引き継がない**
- 仮想的なステアリング / 加速 / 制動コマンドを推定する
- それらをドライバーの実際の操作と比較する
- 差分を可視化・記録する
- ADAS / 自動運転 / AMR 関連の就職応募向けポートフォリオとして提示できる

### 中核コンセプト
このプロジェクトは、公道で車両を制御するための自動運転車の実装**ではない**。  
これは、仮想的な制御出力を生成し、それを人間の運転挙動と比較する**開発・評価プラットフォーム**である。

### 制約
- アクチュエータの介入なし
- 低予算
- ノートPC / 既存ハードウェア / 最小限のセンサを優先
- 3か月でデモ可能なバージョンを完成させる

### ポートフォリオ上の位置づけ
このプロジェクトは次のように説明すべきである:
- **評価プラットフォーム**
- **シャドーモード ADAS プロトタイプ**
- **計画 / 制御比較システム**
- **ROS 2 / Autoware 統合型自動運転実験プラットフォーム**

## 2. 推奨スコープ

3か月で終わらせるには、**完全な自動運転スタック全体を作ろうとしないこと**。

### 維持すべき推奨スコープ
- シャドーモード専用
- カメラ中心の実装
- リプレイ中心の評価
- 最初は1種類の道路シナリオに限定:
  - 直線的な市街地道路
  - 低速道路
  - または固定の反復ルート
- Autoware の利用範囲は以下に限定:
  - planning / path handling / control の参照
  - ROS 2 統合
  - 地図 / 軌道 / 可視化の概念

### 3か月版で避けるべきスコープ
- 公道上での完全リアルタイム自律走行
- 完全な HD マップ作成
- 初日から多数センサを用いたセンサフュージョン
- 重い物体検出の最適化
- 完璧な自己位置推定
- 法規対応を含む完全な機能セット

理由:  
ポートフォリオとしての価値は、量産自動運転スタックを真似ることよりも、**システム設計、評価手法、再現可能な改善**にある。

## 3. システムアーキテクチャ（推奨）

## 3.1 入力
- 前方カメラ映像
- GPS（任意）
- IMU（任意）
- 利用可能なら OBD/CAN 読み取り専用の車速
- 利用可能なら手動運転入力の代理信号:
  - ステアリング角
  - アクセル / ブレーキ推定
  - または自車挙動から導出した運動信号

## 3.2 処理ブロック
1. **データ取り込みノード**
2. **車線 / 道路形状推定ノード**
3. **自車状態推定ノード**
4. **仮想プランナ / コントローラノード**
5. **比較および指標算出ノード**
6. **可視化 / ダッシュボードノード**
7. **ロガー / リプレイノード**

## 3.3 出力
- 仮想ステアリング角コマンド
- 仮想速度 / 減速度要求
- 横方向誤差
- 方位誤差
- ドライバー操作と仮想コマンドの差分
- 警告 / 介入スコア
- 同期済みログとデモ動画

## 5. 週次の運用リズム

毎週、次のサイクルを使う:
1. 狭く明確な目標を1つ決める
2. 最小バージョンを実装する
3. 同じ 2〜3 シナリオでリプレイを実行する
4. 指標とスクリーンショットを保存する
5. 短い技術メモを書く
6. 改善するか凍結するかを決める

理由:  
固定された評価ループがないと、個人プロジェクトは終わりのない試行錯誤に流れてしまう。

## 6. 最小技術スタックの推奨

### ハードウェア
- 既存ノートPCを主計算機として使用
- 前方カメラまたはドライブレコーダー風カメラ
- 専用センサがなければスマートフォンの GPS / IMU
- 任意で読み取り専用 OBD/CAN アダプタ

### ソフトウェア
- Ubuntu
- ROS 2
- 必要に応じて Python + C++
- OpenCV
- RViz
- rosbag
- シンプルな可視化ツール（Python/matplotlib）
- 必要に応じて限定的な Autoware コンポーネント

### このスタックを選ぶ理由
以下のバランスが取れているため:
- 低コスト
- 再現性
- ROS 2 との関連性
- 実証可能なシステム統合価値

## 7. 指標定義テンプレート

これらを `docs/metrics.md` に明確に記録すること。

### 横方向指標
- 車線中心からのオフセット
- 方位誤差
- 仮想ステアリングと実ステアリングの差分
- 経路追従の不一致

### 縦方向指標
- 目標速度と実速度の差分
- 加速度の不一致
- 制動要求の不一致

### 安全性指向の指標
- 警告スコア
- 車線逸脱リスクの代理値
- 可能なら TTC 類似推定
- 可能なら最小停止余裕推定

### 快適性指向の指標
- ステアリング平滑性の代理値
- ジャークの代理値
- 振動 / 不安定性の回数

### ポートフォリオ上のルール
すべての指標は、次のいずれかに答えるべきである:
- システムは妥当に振る舞っているか？
- どのような時にドライバーと不一致になるか？
- その不一致は安全上重要か？
- 改善によって問題は減ったか？
